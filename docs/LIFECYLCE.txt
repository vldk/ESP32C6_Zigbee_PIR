  3. Steady state — the sleep/wake cycle

  This is the part that replaced deep sleep.

          ┌──────────────────────────────────────────────┐
          │  all three tasks blocked, nothing to do      │
          └──────────────────────┬───────────────────────┘
                                 │ stack raises
                                 ▼
                    ESP_ZB_COMMON_SIGNAL_CAN_SLEEP
                                 │
                       esp_zb_sleep_now()          ← drops the stack PM lock
                                 │
                     FreeRTOS tickless idle
                                 │
                                 ▼
                     ╔═══════════════════════╗
                     ║  AUTOMATIC LIGHT SLEEP ║   RAM kept, radio kept,
                     ║   ~40 MHz / CPU down   ║   network join kept
                     ╚═══════════╤═══════════╝
                                 │
          ┌──────────────────────┼──────────────────────┐
          │                      │                      │
     GPIO level             esp_timer alarm       stack poll timer
     (PIR / button)      (hold / heartbeat)       (parent, ~3 s)
          │                      │                      │
          └──────────────────────┴──────────────────────┘
                                 │
                            wake, handle, ──────► back to sleep

  Contrast with the sketch: that path was esp_deep_sleep_start() → RAM gone →
  reboot → radio init → rejoin → then report.

  The level-follower underneath it — the reason edges are never lost across a
  sleep:

     arm LOW ──► [ idle, line HIGH ] ──LOW──► ISR ──► app rearms
                         ▲                                │
                         │                                ▼
                     ISR ◄──HIGH── [ asserted, line LOW ] ◄── arm HIGH

  An edge during sleep would be lost (GPIO clock is off); a level is still there
  when the ISR finally runs. That is why both the wake source and the interrupt
  are level-triggered, always armed for the level the pin does not currently
  have.

  The invariant that keeps this simple: only app_task mutates application state.
  ISRs, esp_timer callbacks and the Zigbee stack task are all pure producers
  into s_events, so there is no lock anywhere in the application — the only lock
  is esp_zb_lock_acquire() around stack calls.
